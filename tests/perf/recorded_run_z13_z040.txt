=== WHAT THE PROFILES NAME, AND WHAT WAS DONE ===
Z-016 padding rule of record: every field written by more than
one thread gets its own 64 B line; guard lines 0; read-mostly
and single-writer fields exempt. The banked nm layout (BEFORE,
offsets in the core object's .bss) showed the defect exactly:
all six core audit counters packed 8 B apart in one line; the
four L1 call counters inside one 32 B span; the J-002 stats
counters - including the two PRE-LOCK atomics - sharing lines
with the lock-held counters and the registry anchors; the TLS
owner table at 24 B per entry (65536 x 24 = 0x180000), so
neighbouring slots written by unrelated threads share lines.

PURGED (each given its own 64 B line; variable TYPES unchanged,
so every test-only extern declaration still binds exactly):
 1. L1 audit call counters x4 (src/api/mimir_alloc.c):
    _Alignas(64) each. Lock-free relaxed fetch_add on EVERY
    public call. AFTER nm (api object): offsets 0x00, 0x40,
    0x80, 0xc0 - one per line.
 2. Core audit mimir_audit_small_alloc / mimir_audit_small_free
    (src/core/mimir_core.c): _Alignas(64) each. These two are
    incremented WITHOUT the lock on the TLS hit path
    (tls_alloc) and the free-to-bin path (tls_free_local) -
    found by source audit during this slice; the other four
    audit counters move only under the lock (see KEPT PACKED).
    AFTER nm: small_free 0x00, small_alloc 0x40 - own lines.
 3. J-002 stats pre-lock pair mimir_stats_alloc_failures /
    mimir_stats_alloc_posture_nulls: _Alignas(64) each.
    Relaxed atomic adds on pre-lock admission paths from any
    thread. AFTER nm: posture 0x...c00, failures 0x...c40 -
    own lines, no longer sharing with the lock-held counters.
 4. TLS owner table entry (Z-029 cache companion): struct
    tls_owner_entry padded 24 B -> 64 B (_Alignas(64) key +
    40 B tail pad; field order and offsets 0/8/16 UNCHANGED -
    the set/get/clear publication order (span, owner, then key
    CAS) is untouched). _Static_asserts pin sizeof == 64 and
    the owner/span offsets. AFTER nm: table size 0x400000 =
    65536 x 64 B. One entry per line, per slot: a block's
    record never shares a line with another block's record.

KEPT PACKED - measured reason, not oversight. The probe's
locked7 pattern (below) proves that scattering a group whose
writes are serialised by ONE mutex COSTS +11..+36% at 8-32
threads: with the packed group one line migrates per lock
hand-off; scattered, every line of the group migrates. The
Z-016 penalty case is CONCURRENT writers; under the global
lock there is exactly one writer at a time. So the locked
groups stay packed, and the purge's job for them is the one
performed above: no lock-free hot field shares their lines
any more (compare the BEFORE/AFTER nm tables,
hidden_files/z040_nm_before.txt / z040_nm_after.txt).
Kept packed: the five lock-held J-002 counters (bytes_requested,
bytes_allocated, bytes_released, peak_mapped,
cross_thread_frees); registry anchors (head, live_mappings,
live_bytes); span anchors (span_head, live_spans,
live_span_bytes, live_small_objects) and mimir_class_active[20]
(all lock-held on every path); the four lock-held audit
counters (alloc_published, mapping_retired, span_published,
span_retired); the TLS tally (4096 x 16 B, lock-held only);
the TLS exit-drain pair (lock-held, thread-exit cold);
the diag counters + guard (atomic but failure-path cold;
their line carries no hot field after this purge).

NOT APPLICABLE register (examined, nothing to purge):
 - Span free lists: the links live IN the freed blocks
   themselves (in-band); no layout change is possible without
   changing the allocator's storage contract - a redesign
   question, not a purge.
 - Span headers / large descriptors: 96 B each, one per
   reserve page; two headers never share a line.
 - Z-030 remote-free queue: test-only header, not wired into
   production mimir_free (Z-030's own dependency honesty);
   already line-separated by its design (its Q0 phase asserts
   the offsets).
 - TLS bins and per-thread counters: _Thread_local, the state
   struct already _Alignas(64) (Z-029).
 - Z-034 out-of-line metadata table: exists only under
   MIMIR_OOL_META, which no production build defines.
 - Lock histograms (z19_hist): MIMIR_LOCK_HIST builds only,
   absent from production objects.
 - Platform mutex: a single object; its line must migrate to
   each acquirer by definition - padding cannot change that.

=== METHOD (probe_z040, Z-004 protocol) ===
Standalone probe replicating each purged group's exact access
pattern in packed vs padded layout (a whole-allocator run
cannot attribute deltas: every public op touches several
groups). Threads pinned physical-first (0-7 CCD0, 8-15 CCD1,
16-31 SMT); median of 5 reps; every rep verified by exact
counter sums (a mismatch aborts the probe); go-flag start as
in probe_z016. Patterns:
 l1mix    4 counters, thread t increments ONLY counter t%4,
          relaxed atomic, no lock (models groups 1 and 2).
 l1same   CONTROL: all threads increment counter 0 - TRUE
          sharing; padding must NOT help, and it does not.
 prelock2 2 counters, thread t increments ONLY counter t%2,
          relaxed atomic, no lock (models group 3).
 owner    per-thread slot in a {key, owner, span} entry:
          atomic load key + fetch_add owner + store span per
          op, entry stride 24 vs 64 (models group 4, aggregate
          over the consecutive-slot geometry the hash produces).
 locked7  7 plain counters under ONE mutex, all incremented
          per op (models the KEPT PACKED groups).
Load state (SHARED HOST, recorded honestly): run 1 (PRIMARY)
started at loadavg 0.41/0.62/0.54; a sibling campaign's pytest
suite ramped during the session (load 11.95 mid-session, 18.30
at the end of run 2). Run 2 is therefore contended; run 3 was
taken during the e2e ladders. The verdicts rest on WITHIN-RUN
packed-vs-padded ratios at fixed thread counts, which
replicate across all three runs within ~2 points on every
WIN cell and exactly on the control (see CORROBORATION) -
the same discipline Z-016 used for its contended finals.

   update falls to 0.26-0.35x at 2-32 threads (l1mix).
 Core audit small_alloc / small_free: WIN - same lock-free
   geometry as l1mix (distinct counters, distinct op streams,

   the harness shows no padded-layout bias, and no claim in

=== FOOTPRINT COST (the purge's bill, stated) ===
Core object .bss: 1,645,120 B -> 4,266,760 B (+2,621,640 B =
owner table +2,621,440 B at 40 B/entry x 65,536, plus 200 B
of counter alignment slack). The owner growth is virtual
zero-page BSS: pages are touched only for slots the hash
reaches, exactly as sparsely as before; the cost is address
space and worst-case RSS if every slot is touched, never
up-front RSS. Counter/tail padding total: under 1 KiB.
