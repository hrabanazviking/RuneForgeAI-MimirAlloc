=== METHOD ===
Adversarial patterns constructed from Z-055's worst cases (tests/perf/recorded_run_z13_z055.txt, banked): F-3 free-but-unusable 32064 B at R-EXT 0.260937 with class-locked holes; fragmented bearing spans in classes 64/256/1024; the class-1024 span tail of 928 B; large-mapping overheads 20000->24576 and 40000->45056; and the Z-048 size-exact mapping pool those frees feed. Each pattern below asks one question of a freed block's space: can it be SPLIT to serve a smaller request, or COALESCED with its neighbours to serve a larger one? Quiescence per Z-055: mimir_core_trim_retained_some(0) flushes TLS bins before every snapshot; all counters are J-002 stats at those points; large-pool state via the Z-048 query pair.

=== PATTERN-BY-PATTERN BEHAVIOUR TABLE (roadmap gate) ===
P1 CARVE-SPLIT (fresh page -> class-64 slots): a span page IS split, once, at span birth - carved sequentially into fixed class slots (20 allocs: 1 span, capacity 62, all offsets multiples of 64 from slot 0, patterns intact). This carving is the ONLY split the small path ever performs, and it is irreversible for the span's life: the span serves exactly one class.
P2 CHECKERBOARD (32 x 64 B, free every other slot): coalescing NO - a class-128 request is served but NOT from any coalesced 64-hole (address outside the freed set); exact-size reuse YES - a class-64 request returns one of the freed holes exactly. Survivor patterns intact.
P3 CROSS-CLASS SPLIT (free a 1024 slot in a span pinned live by a second 1024 block; request 16 x 16 B): split NO - no 16 B block lands in the freed 1024 slot. Confound found and separated by the pin: unpinned, a 16 B block DID land on the freed address - whole-PAGE reuse after the empty span was released and a class-16 span acquired at the same page, not a slot split. The two mechanisms are now distinguished on record.
P4 PIN TRAP (124 x 64 B filled, then all but one freed): at full, class-64 spans=3 live=124 mapped(total)=28672; pinned, spans=3 live=1 mapped=28672 retained(total)=24576. The one live block's span cannot be partially released: release granularity is the whole page. See WORST CASE.
P5 FREE-ORDER REUSE (free A then B, class 64): reuse is exact-slot but NOT strict LIFO and NOT prompt - in the run of record A reappears at batch index 62 and B at 189 of the next 256 class-64 allocations (TLS batching / span distribution order). Both slots are reused whole, never merged, never lost; both further executions reproduced indices 62/189 exactly.
P6 LARGE SPLIT (pool holds freed 45056 mapping; request 20000 = 24576 mapping): split NO - fresh mapping taken (mapped 45056 -> 69632, delta exactly 24576), pool untouched at 1 entry / 45056 B. A pooled mapping serves only its exact length.
P7 LARGE COALESCE (pool holds 45056 + 24576; request 70000 = 77824 mapping): coalesce NO - fresh mapping taken, pool untouched at 2 entries. Pooled mappings are never merged.
P8 LARGE EXACT REUSE (control; request 40000 again): YES - served from the pool at the SAME address as the original block; pool drops by exactly that entry. Exact-length reuse is the pool's only service.
P9 REALLOC (small grow 32->256: moves, contents preserved. Large shrink 40000->20000): split NO - shrink stays in place at the same address and live_mapping_bytes stays 45056 -> 45056: the 25056 B tail is never split off, released, or pooled while the block lives; it is recovered only at free (into the size-exact pool, P6-P8 rules).
P10 WHOLE-SPAN RELEASE (free-all + full trim): the only coalescing-like act in the allocator is at page granularity - empty spans past the retention bound (2 per class) are released whole, and after free-all + trim, mapped returns to the baseline 0 exactly, live_small=0, pool=0. Nothing below page granularity is ever reclaimed.

WORST CASE (named, roadmap gate): P4, the pin trap. One live 64 B block pins its whole 4096 B span page: 4032 B of that page (98.44%) is free-but-unusable - it cannot be split for a smaller class, cannot coalesce toward a larger one, and cannot be released until the last block frees. Measured at the pinned point: 28672 B stood mapped behind exactly 1 live class-64 object (64 B), with 24576 B of retained empty spans beside it. This is Z-055's F-3 (32064 B, R-EXT 0.260937) reduced to its atomic cause: in this allocator fragmentation is never healed inside a page, only waited out at page granularity. Runner-up, large path: P9's shrink keeps a 45056 B mapping for a 20000 B request (25056 B, 55.6% of the mapping, dead until free), and P6/P7 show up to the pool's 32 MiB bound of freed mappings can sit equally unusable for any non-exact size.

=== READING ===
Split: exactly two forms exist - span carving at birth (P1, fixed class slots, one-way) and nothing else. No free block, span slot, pooled mapping, or realloc tail is ever split (P3, P6, P9).
Coalesce: none, at any granularity below the page. Adjacent free slots never merge (P2), freed slots of one class never serve another (P3), pooled mappings never merge (P7). Reclamation is whole-page only (P10), retention-bounded at 2 empty spans per class.
Reuse: exact-size only everywhere - a freed class slot serves only its class (P2, P5, on TLS-batch timing, not LIFO), a pooled mapping only its exact length (P8).
Defects: none in repo / allocator code - every behaviour above is the allocator's documented design (fixed size classes, one class per span, size-exact pool) measured adversarially, not a malfunction. The one probe-side defect found and fixed during the build was P3's unpinned first form, which conflated page reuse with slot splitting; the pinned form is the run of record. No bug is left unfixed; no follow-up is owed by this slice - Z-059 (placement policy trial) inherits P2/P4/P5 as its fragmentation-oracle inputs.
Team structure: lead + 6 Mythic Engineering sub-agents spawned in parallel (design, implementation, gate verification, battery reconciliation, measurement, risk/commit-scope review) - no 429. Reports advisory; every gate fact verified on-device by the lead.
