== PAPER DESIGNS (no code; the decision applies R1-R3) ==
Geometry A - per-thread arenas. Partition: each thread owns
an arena = a private set of per-class span registries plus
its TLS bins; spans are born in one arena and stay owned by
it. Key: owning thread id (arena index = a small integer
assigned at first allocation, Z-037's per-CCD prototype is
the 2-arena stepping stone). Stays global: the mapping
registry (page acquisition/release) behind the one existing
global lock, taken only on span birth/death, not per op.
Cross-thread frees: a free of a block owned by another
thread routes to the owner's Z-030 MPSC ring (bounded,
counted overflow falls back to freeing under the owner's
arena lock); the owner drains in batches of 8 on its next
allocation, feeding its TLS bins. TLS refill/drain: refill
draws from the thread's OWN arena registries under its own
arena lock (uncontended in the common case); drain returns
to the same. Thread exit: arena is sealed, its live blocks
remain valid and freeable via the ring/lock path, its empty
spans return to the global pool through the H-001 drain
machinery; the arena slot is recycled only when empty.
Overhead/RSS risk: per-thread registry state and retained
empty spans multiply worst-case retention by live-thread
count - the Z-042 storm slice exists to price exactly this.
Top hazard: a span migrating or being freed through the
wrong arena corrupts two registries at once; ownership must
be derivable from the pointer alone (span header), never
from the freeing thread. Argued FOR by: arena leg winning
the 8..16 band per R1 (contention was the wound, and
removing shared registries removes it).
Geometry B - lock-sharding of the existing geometry.
Partition: the singleton core keeps ONE set of registries;
the one global lock becomes K shard locks (K = banked
class count is too many; the design shards by class GROUP -
hot small classes each get a shard, cold classes share),
each shard guarding its classes' span lists; the mapping
registry keeps its own lock, always acquired LAST (fixed
lock order: shard -> mapping). Key: size class of the
operation. Stays global: everything else - span ownership
is unchanged, so cross-thread frees need no routing change
at all (a free takes the block's class shard, whoever
frees it); the Z-030 ring stays an assembly option, not a
requirement. TLS refill/drain: refill takes only the
refilled class's shard; drain likewise; two-class
operations (realloc across classes) take both shards in
class order. Thread exit: unchanged from today (TLS drain
under the touched shards). Overhead: K padded lock words
(Z-016 rule) and nothing else; RSS unchanged. Top hazard:
lock-order inversion on the two-shard paths (realloc,
drain) - the fixed order and a lock-order audit in the
slice's suite are the mitigation. Argued FOR by: R2/R3 -
the arena leg tying or winning only at SMT counts says the
wound is lock granularity, not shared state, and B is the
smaller, retention-free change.
DEPENDENCY NOTE for Z-040: the false-sharing purge's target
list depends on which geometry exists (A adds per-arena
structures; B adds the shard array). Z-040 must read the
Z-039 decision record before fixing its target list; while
the decision is pending, Z-040's condition-independent

(TLS state, audit counters, Z-030 rings).
