== METHOD AND DISCIPLINE (H-006 carried forward) ==
"Quiescent" is operational: no thread inside an
allocator call and the global lock not held at the fork
instant. Deadlockable shapes run ONLY in disposable
children under a parent watchdog: poll()+waitpid
(WNOHANG), 500 ms per staged child, then SIGKILL of the
exact pid + reap; every child sets PR_SET_PDEATHSIG;
children use only write()+_exit (the parent fflushes
before every fork); the /proc/<pid>/stat state char is
captured at kill time. "HUNG" in this record means only
"no completion within the 500 ms window" - nothing
stronger is claimed from any single try. Hang outcomes
are quoted as counts, never rates (INC-H006-05).

The staged phases pin the mechanism deterministically:
the core's one global lock IS
mimir_platform_global_lock() (src/platform/
mimir_platform.c, a single static pthread_mutex;
exported in libmimiralloc.a). B0a takes that very lock
in the parent across fork(); B0b takes and releases it
before fork(). There is no pthread_atfork anywhere in
src/ (grep-verified at build time).

== THE BOUNDARY - L-08 AS EXTENDED BY THIS RUN ==
POSTURE RE-CONFIRMED AND EXTENDED. The L-08 core is
unchanged: fork is supported ONLY (1) quiescent and
(2) fork+exec promptly; fork-while-busy is unsupported.
Clause 1 (mutex hazard, INC-Z044-02 = H-006 /
INC-H006-01 re-measured on the current core): if the
core's global lock is held at the fork instant - by any
thread, including one that will not exist in the
child - the child's first locked-path allocator call
does not complete (B0a stages this deterministically,
3/3 in both runs; B1 observes it 24/24 under saturated
churn in both runs). New since H-006: the Z-029 TLS bin
hit path does NOT take the lock, so a busy child whose
bins are primed completes small allocs and still hangs
on the first locked-path call - "the small one worked"
is not evidence of safety.
Clause 2 (span stranding, INC-Z044-01, NEW in Z-044):
in a multithread-quiescent fork, spans whose binned
tally belongs to threads that do not exist in the child
cannot be released in the child even after every
inherited live block is freed and the child's own bins
are drained (Q2: 2 spans stranded of the workers'
spans, drain_released=0, in both runs). The child's
memory floor is bounded below by those spans for the
child's whole life. No corruption was observed: the
integrity claim is scoped to the checks performed
(pattern verification of every inherited block, all
frees completing, clean exits).
Accounting note (same root as Clause 2's visibility):
the child's stats counters inherit the flushed view;
vanished threads' unflushed pending transitions make
the child's counters inexact by small bounded amounts
(Q2: -3 at entry, -1 residual). The parent is wholly
unaffected (settled 0/0).
Practical rule, unchanged in shape, sharper in detail:
a forked child of a mimir process may only exec or
_exit without calling any allocator entry point, unless
the fork was quiescent - and a quiescent multithread
child that allocates must tolerate stranded spans and
inexact counters. A BOTH_OK busy child (none occurred
for mimir in this run; 24/24 for glibc) would mean only
"no hang observed in that child within the window" -
not support, not a fix, not safety.
