=== METHOD ===
One probe source, two legs (mimir = this tree's banked allocator with the Z-048 mapping cache and Z-049 THP posture live; glibc = host malloc/free). Every pattern allocates ONLY large-path sizes (all requests above the 1024-byte small cutoff) and dense-touches every block (memset of the whole extent) so RSS is real resident memory, not reservation. At each defined phase the probe reads its own /proc/self/smaps_rollup (Rss + Pss - the Z-006 method; VmRSS spot readings are NOT used anywhere, per the Z-047 census lesson) and /proc/self/maps in the same instant.
Patterns (roadmap: interleaved large sizes over long runs):
  checker   192 blocks alternating 64 KiB / 256 KiB. Phases FULL, HOLED (the 256 KiB blocks freed - size-mismatched holes), REFILL (the same 256 KiB blocks re-allocated), DRAINED (all freed).
  uniform   256 blocks of 128 KiB (control). FULL, HOLED (every second block freed - exact-size holes), REFILL, DRAINED.
  pinwheel  128 blocks cycling 16 KiB / 1 MiB / 32 KiB / 512 KiB. FULL, THIRD1 (every 3rd freed), THIRD2 (the next third freed), DRAINED.
  churn     the long run: a 96-slot live window, 6000 replace operations (free one slot, allocate a fresh size from {16 KiB, 32 KiB, 64 KiB, 128 KiB, 256 KiB, 512 KiB, 1 MiB, 2 MiB}, dense-touch). Checkpoints OP0 / OP1500 / OP3000 / OP4500 / OP6000, then DRAINED. Slot and size choices come from one fixed-seed xorshift PRNG, so both legs execute the identical operation sequence.
Metrics per phase: live_count / live_bytes (requested bytes held live); vma_count and vma_delta vs the same process's BASE phase; Rss / Pss (smaps_rollup); allocation VMAs (VMAs holding at least one live block) and their total bytes; holes = unmapped-or-pooled address gaps between consecutive allocation VMAs (gaps of 64 MiB or more separate distinct regions - heap vs mmap area - and are excluded); the truly-unmapped part of those gaps (pooled mappings inside a gap are mapped, not holes in the address space); gap_bytes = address gaps between consecutive live blocks (capped at 64 MiB for the same reason).
Fragmentation factors (the roadmap gate quantity), per process then median across processes (Z-004 headline discipline): rss_factor = Rss / live_bytes (gross blow-up); net_factor = (Rss - Rss_BASE) / live_bytes (resident bytes the allocator holds per live byte - the headline factor); win_factor = allocation-VMA bytes / live_bytes; hole_frac = hole bytes / (allocation-VMA bytes + hole bytes). The worst-case factor per pattern is the maximum median net_factor over live phases; the absolute worst single process is printed beside it. Processes: 3 measured per leg per pattern + 1 warm-up per leg per pattern discarded, pinned taskset -c 2, legs interleaved within each round (run_z053.sh).
Workload equivalence: the probe verifies the first and last stored byte of every live block at every phase (a mismatch aborts the process), and the checksum (sum of those bytes over live blocks) is a deterministic function of the operation sequence. The summariser proves ALL (pattern, phase) checksums identical across legs and processes - see the first line of the summary below.
Definitions caveat (kernel VMA merging): adjacent anonymous mappings with identical permissions merge into one VMA. A FULL phase of 96-256 sequential large allocations therefore shows vma_delta of only about +1 for BOTH allocators - VMA count growth appears when frees break the merged region apart, which is exactly what the HOLED / THIRD / OP phases measure. FULL-phase vma_delta varied 0..+1 across smoke runs of both legs (merge-layout nondeterminism); all recorded-run values below are the medians of the run of record.

=== READING - FRAGMENTATION FACTORS PER PATTERN (roadmap gate) ===
Gate: "fragmentation factors recorded per pattern" - MET. The factors of record (median net_factor = resident bytes held per live byte, worst live phase; gross rss_factor beside it):
  checker   mimir 3.804 at HOLED (gross 4.131)   glibc 1.031 at HOLED (gross 1.354)
  uniform   mimir 1.559 at HOLED (gross 1.682)   glibc 1.043 at HOLED (gross 1.164)
  pinwheel  mimir 2.537 at THIRD2 (gross 2.656)  glibc 1.077 at THIRD2 (gross 1.194)
  churn     mimir 1.634 at OP6000 (gross 1.678)  glibc 1.480 at OP6000 (gross 1.523)
At every FULL / OP0 phase both allocators sit at net 1.006..1.037 - an interleaved large live set, densely touched, costs essentially its own bytes under either allocator. Fragmentation is a property of the FREE pattern, not the allocation pattern.

F1 - The holed-phase blow-up is the Z-048 pool's retention price, and it is bounded by the pool's own design bounds. When checker frees its 256 KiB blocks, MimirAlloc does not unmap them: exact-length mappings go to the mapping cache (up to 64 mappings / 32 MiB) with their dense-touched pages still resident. The live set that remains is the small 64 KiB half (6 MiB), so resident-per-live peaks at 3.804x. glibc, which unmaps freed mmap chunks and returns arena memory differently, peaks at 1.031x on the same phase. Grade on this phase, in roadmap words: LOSS for MimirAlloc - a real, measured RSS blow-up, bought deliberately at Z-048 for the 42.3x large_batch win, capped by construction, and spendable by Z-050's trim policy (the very next Wave 6 policy slice). It is not unbounded growth: see F4.
F2 - Address-space holes and RSS holes are different quantities, and the two allocators trade them. In uniform HOLED, glibc shows the worse ADDRESS fragmentation (127 allocation VMAs, 126 holes, hole_frac 0.528, 17.0 MiB truly unmapped between live blocks) but the better RSS factor (1.043 - unmapped holes are not resident). MimirAlloc shows fewer unmapped holes (8.6 MiB; the rest of its gaps are still-mapped pooled entries) but holds the resident bytes (1.559). Any future fragmentation fix must name which quantity it is buying down; Z-058's split/coalesce audit inherits this distinction.
F3 - Refill is exact for MimirAlloc. In both checker and uniform, REFILL reproduces FULL to the KiB on every metric (RSS 33700 / 36000 KiB, vma_delta back to +1, one hole of the FULL size): the holes the free pattern made - pooled or unmapped - are fully reusable by the same sizes, and no residue accumulates across a free/refill cycle. glibc's uniform REFILL keeps its 126-hole address fragmentation (hole_frac 0.361 at REFILL vs 0.000 in its checker REFILL) while its RSS also recovers - address fragmentation can persist across refills under glibc where MimirAlloc's does not.
F4 - The long run grows, then is capped by the same pool bounds. Across churn's 6000 ops, MimirAlloc's vma_delta climbs +1 -> +6 -> +23 -> +31 -> +35 and its net factor settles in a 1.48..1.63 band from OP1500 on (no runaway trend in the last three checkpoints: 1.588, 1.478, 1.634 against a changing live set). At DRAINED it retains 28956 KiB net RSS across 45 VMAs - under the pool's 32 MiB / 64-VMA bounds, i.e. the retention ceiling is the design bound, not the workload size. Checker DRAINED retains only 4556 KiB / 61 VMAs (its pool fills by count with small mappings), pinwheel 25804 KiB / 43 VMAs. glibc retains 320 KiB (checker/uniform/churn) to 1728 KiB (pinwheel) at DRAINED - glibc returns nearly everything; MimirAlloc's DRAINED retention is the pool, held for reuse until trim or drain (Z-048's accounting: Q-RELEASED moves only at an actual munmap).
F5 - Pinwheel's staircase shows the pool absorbing the first release wave whole: at THIRD1 MimirAlloc's RSS does not move at all (53404 KiB, identical to FULL; unmapped hole bytes just 8192) while live bytes fall by a third - every first-third free was pooled. The cost lands at THIRD2 (net 2.537) once the pool is full and later frees both unmap and strand resident neighbours. glibc's staircase is the mirror image: RSS falls at every step (net stays ~1.03..1.08) while its unmapped holes grow to 31.6 MiB (hole_frac 0.631).

Bugs found in this slice's own tooling, fixed before the recorded run (no production code touched; no production bug discovered): (1) the first window definition (address span from lowest to highest live block) charged the heap-to-mmap region distance (tens of TB on glibc legs, whose small-large blocks live in two regions) to "holes" - replaced by the allocation-VMA gap definition above, with the 64 MiB region cap applied to block gaps as well; (2) the gap metric originally could not distinguish pooled (still-mapped) gap bytes from truly unmapped holes - the unmapped-part walk was added, which is what makes finding F2 stateable; (3) the summariser printed every phase twice (its phase list was built over both legs) - fixed after the run; display only, numbers byte-identical.
