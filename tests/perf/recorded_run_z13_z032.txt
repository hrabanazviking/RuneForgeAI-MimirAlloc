method: (1) MAP - for every request size r in 1..1024, 6 blocks are
  allocated and the serving class is derived as the minimum absolute
  stride between consecutive returned pointers (carve order and
  free-list LIFO order both step by exactly the class size inside a
  span; a span crossing is a strictly larger jump, and a same-span
  pair always exists at 6 blocks, so the minimum stride is the class
  and is immune to reuse order and span boundaries by construction).
  (2) SPAN - one fresh process per class: the count of consecutive
  allocations landing on the first block's 4096 B page is the true
  objects-per-span (first span in a fresh process is a fresh carve).
  (3) CACHE - per exact class, 2048 blocks live at once, 2 rounds
  (fresh carve, then free-list reuse), ptr mod 64 buckets, sub-16
  count, cacheline-split count, min alignment (the Z-017 shape, at
  half Z-017's n; distributions reproduce Z-017's exactly).

Structural fact (both audits): every class that is a multiple of 64
returns pointers exclusively at ptr mod 64 = 32 - carve starts at page
offset 96 (the span header) and strides by a multiple of 64, so starts
stay at 96 mod 64 = 32 forever. Class 64 therefore splits 100% and
class 48 splits ~half (offsets 32/48 straddle). This is fixed by the
HEADER/CARVE OFFSET, not by which class sizes exist: any table keeps
offset 96. Spacing cannot repair it; see the verdict.

=== VERDICT - DECISION FOR Z-033 ===
DECISION: NO-CHANGE. The current 20-class table (16, 32, 48, 64, 80,
96, 112, 128, 160, 192, 224, 256, 320, 384, 448, 512, 640, 768, 896,
1024) remains in force; no candidate table is adopted, and Z-033's
conditional trigger (implement Z-032's adopted table) is NOT met.
Basis, from the tables above (identical geometry and models for
every candidate): the best finer candidate, C2 step-16 (64 classes),
moves the uniform model's span-effective mapped figure from
638.79 B/request (C0) to 582.99 B/request - an 8.74% model-only
gain that fails the 10% bar and triples the class count (retention
ceiling 524,288 B vs 163,840 B). C3 and C4 (the efficient midpoint
points) gain only 4.29% / 4.47% on the same model. C1 powers-of-two
regresses decisively (+36.85% mapped, +127.75 B mean internal
waste) and is rejected outright. Z-033 is closable as a recorded
no-op citing this run; it must not be left dangling as conditional.
Reasons, in the order the evidence weighs:
1. HISTOGRAM: there is no measured real-world request distribution
   on this host to fit a table to. The landed histograms are the
   campaign's own synthetic cycles drawn FROM this table; their
   zero waste is circular and proves fit to those cycles only.
   Every finer table's gain exists only inside the uniform
   arithmetic model, which weights requests above 512 B at 50% -
   exactly the region where real small-object workloads are
   thinnest and where this campaign has no trace at all.
2. CACHE: the Z-017-named defects (48 B at 49.41% split, 64 B at
   100% split) are carve-offset geometry, reproduced exactly by
   this probe (48 B 49.41%, 64 B 100.00%, every multiple-of-64
   class pinned to ptr mod 64 = 32). Object k starts at
   (96 + k*class) mod 64; with the 96 B span header that residue
   is 32 for class 64 at every k, and cycles 32/16/0/48 for
   class 48 (predicted 50%, measured 49.41%). NO class table
   changes offset 96, so no spacing retune can repair either
   class - and promoting 48 to a 64 stride would make it worse
   (100%). The lever that fixes 64 B fully is the header/carve
   offset (first object at a 64 B-aligned offset: header padded
   to 128 B, shrunk to 64 B, or moved out-of-line); 48 B would
   additionally need a per-object stride decision (64 B-aligned
   carving costs 16 B/object). That is span-layout work for the
   ledger to assign (Z-034's metadata diet is the nearest Wave 4
   neighbour), NOT a Z-033 spacing implementation.
3. SPAN-COUNT COST (measured, Z-024): the small-path free cost is
   dominated by two linear registry walks priced by LIVE SPAN
   COUNT (512 B batch: 1,171 spans, 5,668.0 ns steady free; 64 B
   batch: 133 spans, 444.1 ns). Every added class spreads a fixed
   live set over more spans and adds its own retained empties;
   finer tables pay this measured cost to buy an unmeasured,
   model-only fragmentation gain. Span geometry also eats the
   naive gain directly: e.g. candidate class 576 has the same
   6 objects/span as 640, so it saves 0 mapped bytes for requests
   513..576 despite saving 64 B of internal waste on paper.
4. G-002 AFFIRMED, not re-argued: G-002 already rejected the
   powers-of-two and step-16 tables. This study's new evidence -
   a measured full request->class map, span-effective pricing
   (G-002 priced internal waste only), and retention pricing -
   lands on G-002's side with stronger numbers: both rejected
   tables stay rejected, for the record, on this machine.
5. THE 1024 TAIL: the largest single overhead in the table is
   span geometry, not spacing - class 1024 holds 3 objects per
   4096 B span (928 B tail, +341.33 mapped B/object). No class
   table changes floor(4000/1024). G-002's deferred two-page-span
   alternative is RE-DEFERRED with its reason unchanged and now
   priced: it is a span-size change, outside this slice's gate
   (the class table) and outside Z-033's conditional wording.
