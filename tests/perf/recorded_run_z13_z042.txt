THE STORM SHAPE (tests/perf/probe_z042.c, one process per rep; Z-004 protocol: one warm-up process per leg discarded, then 3 recorded processes per leg, alternating):
Per churn thread: 8 blocks in each of classes 16/64/256/1024, one 2048-byte large block, plus two blocks (64 and 512) left LIVE at exit and handed to main through the thread's argument slot - 35 allocations, every block pattern-touched (first/middle/last bytes, seed a function of thread id, sequence and size) and verified before free. The 33 non-held blocks are freed by their owner thread into its own TLS bins. Threads run in waves of 32 concurrent (the host's hardware-thread count), 10,000 threads per storm. The checksum folded from the verified pattern bytes is reset before the storm phase in both legs, so the STORM checksum covers the storm only: it is 89250992 in all 6 recorded reps, both legs - the two legs did identical work (K-002 discipline).

PHASES AND THE IDENTITIES THEY ASSERT (mimir leg; every snapshot at a quiescent point, after all threads of the phase are joined; full CHECK lines in the raw section below):
  S0 pristine: process start, nothing allocated through mimir yet (all counters 0).
  CAL calibration: ONE thread runs the exact storm shape and captures its own TLS snapshot just before exit: cached_blocks=46, cached_bytes=14912 (identical in every rep). Asserted: exit_drains +1 exactly, exit_drain_blocks +46 exactly - the destructor returned precisely the blocks the calibration thread's bins held, no more, no fewer.
  DRN exactly-once: 256 threads run the shape but call mimir_tls_cache_drain_thread() before returning. Asserted: every post-drain snapshot shows 0 cached blocks, exit_drains +256, exit_drain_blocks +0 - an explicit drain and the exit destructor together return every block exactly once; a double-return would appear here as a nonzero blocks delta or a metadata violation.
  NUL control: 10,000 threads that never touch the allocator. Asserted: exit counters and allocator state do not move at all (a thread that never initialised TLS is never counted as a drain).
  STM the storm: 10,000 churn threads. Asserted: exit_drains +10000 exactly; exit_drain_blocks +460000 exactly (= 10000 x the calibration thread's 46); a settle re-read 100 ms after the joins returns identical counter values (no drain still in flight at snapshot time); live_small_objects after the storm is exactly baseline + 20000 (the held blocks, per class +10000 at 64 and +10000 at 512, nothing else live); J-006 metadata check 0; zero alloc/pattern/create failures.
  HELD post-exit frees: main verifies and frees all 20,000 held blocks of the dead threads. Asserted: held count exactly 20000, live_small_objects returns to baseline, exit counters frozen throughout (main's frees are not exit drains).
  TRIM byte-exact close: main's own cache snapshot is 0 blocks (its frees were all remote, routed to the core); mimir_core_trim_retained() releases exactly the retained spans counted at the pre-trim snapshot (9 spans, 36864 B, every rep); final snapshot: retained 0, bytes_cached 0, bytes_mapped == the pristine S0 figure TO THE BYTE (0), live_spans and live_mappings back to S0. This identity - not the retained figure alone - is the leak proof: any span or mapping the storm failed to account for would survive the trim and appear here.
  At EVERY snapshot, three cross-surface identities are asserted: bytes_cached == mimir_core_retained_bytes() (two surfaces, one quantity); bytes_cached == (sum of per-class empty spans) x 4096; bytes_mapped == live span bytes + live mapping bytes. J-006 metadata check is 0 at all 8 snapshots of every mimir rep. Total across the raw file: 162 CHECK lines, 0 FAIL.

RETAINED-BYTES-AFTER-STORM FIGURE (the gate's named figure): 20480 bytes in every recorded rep (5 empty spans of 4096 B). Decomposition: these are empty small-path spans held by the G-007 retention policy (bound 2 per class, read from the allocator at runtime; policy cap for the touched classes is far above the figure, and the all-class cap is 163840 B). The figure is legitimate retention, not a leak, and the proof is the TRIM phase of the same process: after the held blocks are freed, the retained set is 9 spans / 36864 B, trim releases exactly those 36864 B, and bytes_mapped returns to the pristine 0. A pre-recording trial run of the same probe recorded 24576 B (6 spans) at S1: the one-span variance is which spans the final waves' held blocks happen to vacate, it is bounded by the same policy, and the post-trim identity - the arbiter - held in the trial and in every recorded rep.

DRAIN COST (honest form): the tss destructor runs inside pthread teardown, so no per-drain timer exists that does not also time thread creation. Reported instead: storm wall vs the same-process null-thread wall (10,000 create/joins with no allocator work), per rep, and their difference divided by the exact exit-drained block count as an UPPER-BOUND drain-inclusive figure (it also contains all alloc/free work; it is never a pure drain price).
