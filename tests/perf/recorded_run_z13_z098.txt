Against the BEST TUNED glibc per workload - the column this slice exists to create - MimirAlloc records LOSS on all four workloads. Tuning itself: TUNING WIN on large_batch (-98.70%) and mixed_lifecycle (-57.90%), TIE on small_churn and mixed_batch (no tuned config beats default beyond noise).
small_churn: mimir 29.27 ns/op vs default glibc 3.34 (8.76x, LOSS) and vs best tuned 3.32 [gmm32k, mmap_threshold=32768] (8.82x, LOSS). Tuning TIE (-0.60%).
mixed_batch: mimir 29.35 ns/op vs default 3.72 (7.89x, LOSS) and vs best tuned 3.71 [gtmax64k, tcache_max=65536] (7.91x, LOSS). Tuning TIE (-0.27%).
large_batch: mimir 98.07 ns/op vs default 685.65 (0.14x, WIN, -85.70%) but vs best tuned 8.92 [gcombo_cache, tcache_count=64 + tcache_max=65536] (10.99x, LOSS vs tuned). REASON NAMED: default glibc pays the mmap path for every large block (685.65 ns/op); raising tcache_max to 65536 with tcache_count=64 lets tuned glibc cache and reuse those blocks at 8.92 ns/op, a -98.70% TUNING WIN that erases the default-leg advantage MimirAlloc holds. MimirAlloc large path still pays its per-op mapping/registry cost (98.07 ns/op), so the win over default glibc does not survive the fair fight.
mixed_lifecycle: mimir 517.89 ns/op vs default 7.15 (72.43x, LOSS) and vs best tuned 3.01 [gcombo_cache] (172.06x, LOSS). REASON NAMED: the per-allocation small-path cost documented since Z-003/Z-024 (registry/span walks) dominates the lifecycle shape, and tuning widens the gap (glibc gains -57.90% from the combo cache while MimirAlloc pays the same fixed path cost).
