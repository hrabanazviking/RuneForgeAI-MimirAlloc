DESIGN (smallest wiring that meets the gate)
- D-01 (INC-M002-01) as banked: every unlock call discards its status; a failed unlock would wedge every later call with no counter, no report, no termination. Owed: a post-unlock failure tally.
- Tally: _Alignas(64) static uint64_t mimir_stats_unlock_failures in mimir_core.c (own cache line, the Z-016/Z-040 atomic posture), incremented by a single __atomic_fetch_add at the unlock site. The recording path takes NO lock - after a failed unlock the lock state is unknown by definition, so a lock-taking recorder would be exactly wrong.
- Wiring: every central unlock in mimir_core.c now routes through one counted wrapper - core_global_unlock() for the global lock (41 former (void) call sites, the stats snapshot's own unlock included, plus the one direct shard_unlock_global_all call site), core_shard_unlock() for per-shard unlocks in MIMIR_LOCK_SHARD builds (7 call sites, incl. shard_lock_all's rollback and core_central_unlock). The wrapper calls the name with its current macro meaning in this file: the real L6 entry (production), shard_unlock_global_all (shard builds; the composite body still names the real primitives and leaves counting to its callers, so a composite failure counts exactly once), z19_unlock (MIMIR_LOCK_HIST builds; it forwards to the real entry and returns its status, counted exactly once). Call sites keep their (void) posture: counting is observability, not a new failure mode, and no caller gains a wedge it did not already have.
- Reporting surface: struct mimir_stats gains uint64_t unlock_failures APPENDED AT THE END (every earlier field keeps its offset), copied by mimir_core_stats_snapshot under the lock from the atomic. A failure of the snapshot's own unlock is counted after the copy and appears in the NEXT snapshot - and immediately in the getter.
- Lock-free getter: uint64_t mimir_core_unlock_failures(void) (mimir_core.h, beside the snapshot; one atomic load). It exists because the locked snapshot cannot be taken in precisely the state D-01 feared (mutex wedged by a truly failed unlock); the TRUE injection leg below is unprovable without it. Internal only, same shape (b) as the snapshot; nm -D stays exactly 4.
- No design doc: the change is one counter, two wrappers and one appended stats field, fully described here and in the code comments; no ledger decision was needed (the roadmap gate names the tally itself).

INJECTION PROOF (I-004 shim heritage, extended)
- Instrument: tests/core/mimir_unlock_shim_z064.c - the I-004 --wrap road applied to the one L6 entry I-004 did not wrap, mimir_platform_global_unlock. Test-only object; no production object carries injection code. Two single-shot modes: REPORT (real unlock performed, ERR_LOCK returned to the core) and TRUE (real unlock NOT performed, ERR_LOCK returned - a genuine failure's exact state). Injected and genuine failures are counted separately, as in I-004.
- Build fact proven during the slice (recorded honestly): under the plain LIBOBJS link the shim saw ZERO attempts - the -flto production build (Z-035) inlines the one-line L6 unlock wrapper into the core, leaving no call to interpose on. The test therefore links a -fno-lto build of the leaf platform object ONLY (same source, same -O2); the core object under test remains the production -flto object. Makefile comment records this.
- CONTROL leg: two mixed small/large workloads, no injection: snapshot tally 0, getter 0, while the shim saw 42 real unlock calls (the Z-029 TLS cache serves most small traffic without the central lock; large-path and snapshot unlocks account for the 42) and 0 genuine failures.
- REPORT leg: one armed failure -> snapshot tally exactly 1, getter 1; a full workload then succeeds with the tally unmoved (the allocator's handling of a reported unlock failure adds no wedge); two more armed failures (alloc site, free site) -> tally exactly 3, getter 3.
- TRUE leg (forked child): armed true failure on a large allocation's unlock. The allocation still returns its block (the unlock is post-publication); the tally moves 3 -> 4 read back through the lock-free getter (a locked snapshot is impossible in that state); the child makes no further lock-taking call and exits 0 within 10 ms of fork (bound 10 s). Parent tally stays exactly 3 (process copy) and the parent keeps allocating. A failed unlock is now counted and reported in both injection modes; in the mode where the mutex is genuinely left locked, the tally is still readable and the harness process terminates promptly instead of hanging silently.
