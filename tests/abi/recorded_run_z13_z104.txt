LSan (inside ASan by default on this platform) reported no leaks: the allocator retained spans stay reachable from its globals, as designed.
- Controls: both DETECTED (ASan heap-buffer-overflow on a glibc block, exit 1; UBSan runtime error on signed overflow, exit 1) - the clean suite is not a vacuous pass.
- Coverage boundary (measured, probe exit 0): ASan redzones cover glibc heap (byte-past poisoned=1) and do NOT cover mimir-served blocks (byte-past poisoned=0), because mimir blocks are carved from the allocator own mmap spans. So the sanitizer legs validate the allocator code paths, its stack/global state and its glibc-heap test scaffolding - they do not watch client traffic inside mimir spans. That traffic remains covered by the MIMIR_DEBUG redzones/quarantine (J-004/J-005) and the Wave-8 metadata detection (Z-103 grades it at scale). No coverage beyond this boundary is claimed.
- F-104-1 (FILED, owner named): clang 22 cannot compile src/core/mimir_core.c - it rejects the __atomic_* builtins applied to _Atomic-qualified pointers (122 __atomic call sites in that file; first at line 783). The other two library sources pass clang under the full extended set with -Werror. The shipped compiler is cc/gcc, under which the code is warning-clean, so this is a portability LOSS for a future clang build, not a defect in the shipped build. Owner: the next core-touching portability slice (production roadmap PBR-053 line) - the fix is a deliberate migration of the core atomic surface to C11 atomic_fetch_add-style operations or plain-pointer casts, far outside this matrix slice scope; it is recorded here and in the slice doc, not silently dropped.
- Bugs in production code: none found. One runner defect (log dir under build/) found by the matrix first runs, fixed in the runner before the recorded runs, recorded above.
