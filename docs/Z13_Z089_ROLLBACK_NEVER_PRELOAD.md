# Z-089 - Rollback and never-preload packet

Roadmap slice Z-089: one-variable rollback proven from
a broken state; the never-preload list (display
manager, systemd, the banking tooling itself) written
as an ops doc with reasons. Gate: rollback drill
recorded; ops doc in-tree. Both halves are met: the
drill is tests/abi/recorded_run_z13_z089.txt
(generated by tests/abi/run_z089.sh, standalone via
`make test-z089`, RESULT PASS, zero FAIL lines), and
this doc is the ops doc.

## S1 The rollback drill - design and result

Broken state, honestly contained. The drill subject
is only a harness process the runner spawns
(build-time copy of tests/abi/harness_z089.c in a
private mktemp root). The broken state is that
spawned harness preloaded with a deliberately
poisoned allocator (tests/abi/poison_z089.c, built
into the temp root at drill time): its malloc,
calloc and realloc always return NULL. No real
program, service, display manager, systemd unit or
live desktop process is ever preloaded, attached to,
or signalled to create the broken state - the drill
records the live PIDs of PID 1 (systemd), sddm,
plasmashell and kwin_wayland before and after and
proves them identical.

Result, from the recorded run (loadavg 0.56-0.60,
quiet window; the drill asserts functional behaviour
only and claims no timing numbers):

| leg | invocation | result |
| --- | --- | --- |
| control | harness, no preload (glibc) | rc 0, `HARNESS-RESULT: OK checksum=139217` |
| healthy preload | harness + LD_PRELOAD=Z-082 interposer | rc 0, output byte-identical to control |
| BROKEN x2 | harness + LD_PRELOAD=poison.so | rc 3, `HARNESS-RESULT: BROKEN allocation returned NULL`, deterministic across both runs |
| ROLLBACK | identical command, LD_PRELOAD unset | rc 0, output byte-identical to the glibc control |

One-variable proof (recorded run S5): the environment
of the broken and rolled-back invocations is dumped
from INSIDE each process by a zero-allocation dumper
(tests/abi/envdump_z089.c, write(2) only, so it runs
truthfully under the poison) and diffed sorted:
exactly ONE line differs - the removed LD_PRELOAD
line; zero lines added. No file, package, service or
second variable changes between broken and healthy.
Rollback is unsetting that one variable, as Z-086
already showed for a contained desktop app and this
drill now shows from a genuinely broken state.

Drill defect found and fixed in-slice: the first
version of S5 dumped the environment with
/usr/bin/env, which on this host allocates at startup
(Rust coreutils) and died under the poison
("memory allocation of 24 bytes failed"), so the
diff measured the dumper's breakage, not the
invocations. Fixed by the zero-allocation dumper
above. The failure is kept here as evidence of how
total an always-NULL allocator's breakage is: even
`env` does not survive it - one more reason the
never-preload list below is not caution theatre.

## S2 The never-preload list (ops law for this host)

NEVER set LD_PRELOAD on, export it toward, or bake it
into the unit file / session of, any of the following.
Preload only per-command, on a process you spawn for
the purpose, whose rollback is unsetting the variable
for the next spawn (S3).

1. systemd - PID 1 and the user manager.
   Reason: the preload is inherited by every child the
   manager spawns (account-wide in the user manager).
   A broken allocator there is not a broken program,
   it is a broken machine: no clean rollback exists
   short of reboot or rescue media, and the rollback
   in S1 works precisely because a fresh process is
   spawned without the variable - PID 1 cannot be
   respawned that way. Evidence posture: this campaign
   has never preloaded any systemd process and never
   will; Z-086's containment was designed around
   exactly this boundary (private dbus-run-session,
   never the live user bus/manager).
2. The display manager (sddm on this host).
   Reason: circular gating. sddm owns graphical login
   and spawns the session; if its allocator breaks,
   the failure presents as "cannot log in", and the
   person who would unset the variable is locked out
   by the very process that is broken. Rollback must
   never depend on a component the breakage disables.
   Evidence posture: Z-086 recorded sddm's session
   untouched and tested only contained duplicates;
   nothing in Wave 10 licenses preloading the live
   greeter.
3. The banking tooling itself - git, ssh, gh and the
   keeper/banking scripts for this repo.
   Reason: circular dependency, the sharpest form.
   Banking is the road by which allocator slices are
   merged, pushed (Yrsa SSH identity only) and
   remote-verified; if that road's own processes run
   under a broken preload, the tool you need to bank,
   verify - or to fetch and roll back the library -
   is itself broken, and a silent failure there risks
   corrupting the record of what is banked, not just a
   workload. Z-084 ran git as a one-shot SPAWNED
   battery subject and it passed; that is evidence
   about a spawned subject, not a licence to preload
   the seat's own git/ssh persistently. The drill
   proves the point positively in S7: after the drill,
   the repo's git runs healthy on glibc, never
   preloaded.
4. The live desktop session - plasmashell,
   kwin_wayland and the live session dbus bus.
   Reason: the owner's working session is a single
   point of failure with unsaved state; preloading it
   risks the session itself, and Z-086's evidence
   covers only contained offscreen duplicates (full
   plasmashell in containment was ENV-ONLY: it
   segfaulted identically on the glibc control, so it
   is NOT TESTED as a live preload subject at all).
   What is proven safe is the contained pattern, not
   the live session.
5. Package management and repair tooling - apt/dpkg,
   ldconfig, the compiler/linker used to rebuild.
   Reason: these are the repair path. If an allocator
   change ever does break something, the tools that
   reinstall, relink and rebuild must be running on
   stock glibc, or the repair inherits the breakage.
   Same circularity class as (3), one level down.
6. sshd and any remote-recovery path.
   Reason: remote access is the out-of-band rollback
   when the local session is lost; a preload that
   breaks sshd removes the recovery channel at the
   moment it is needed. Never preload the door you
   would climb back through.
7. Long-lived shared services generally - the host
   Ollama system service is the filed example.
   Reason: a service's other users inherit your
   experiment, and a service restart is not a
   one-variable rollback for them. Z-085 preloaded
   only PRIVATE server instances it spawned on a
   scratch port; the host service on :11434 was never
   preloaded and was left running untouched, and that
   split is the standing rule.

8. Backup and restore tooling.
   Reason: untested in every banked slice, and its
   failure mode is the silent kind: Z-084 showed a
   small contract divergence quietly breaking pattern
   matching in a common tool, and a backup whose
   exclusions, filtering or verification misbehave
   that way is only discovered when a restore fails.
   The tool that must be trustworthy when everything
   else has gone wrong runs on stock glibc.
9. Performance-critical Python jobs and Ollama /
   model loaders (as a performance exclusion).
   Reason: direct Z-085 measurements - correctness
   PASS but Python 5.01x slower overall and Ollama
   model load ~22-24x slower under the interposer.
   Correctness alone does not justify preload where
   the work is time-critical; this class is excluded
   on perf grounds until a later slice re-proves the
   numbers, separate from the correctness pattern in
   S3 (a private, non-time-critical spawned instance
   remains a proven-correct subject there).

## S3 What MAY be preloaded, and how (the proven pattern)

- Per-command environment only: `LD_PRELOAD=<lib>
  <command>` on a process you spawn; never export it
  in a shell profile, never write /etc/ld.so.preload,
  never add it to a systemd unit or a session.
- Spawned, one-shot subjects with a glibc control leg:
  the Z-084 pattern (coreutils, git, python3, bash and
  the repo's own binaries all PASS as spawned
  subjects, proven-loaded + exit 0 + output parity).
- Contained duplicates of desktop apps: the Z-086
  pattern (private HOME/XDG root, private bus,
  headless platform, live session PID-proven
  untouched).
- Private instances of services you start yourself
  on scratch ports: the Z-085 pattern (correctness
  PASS for Python and a private Ollama instance).
- Known limits ride along, honestly: under the
  interposer, `grep '^...'`-style leading-anchor
  regcomp fails by the D-013 zero-size NULL contract
  (Z-084 triage T-084-1, a decided contract, not a
  defect), and perf is a LOSS on the Z-085 workloads
  (Python 5.01x total, Ollama model load ~22-24x)
  even where correctness is exact. "May preload" means
  functionally proven for spawned subjects - it does
  not mean fast, and it never extends to S2's list.
